# 工具使用说明

工具签名由 function calling 自动提供。本文档记录 Agent 使用工具时必须遵守的规则。

## 日历

- 用户询问“今天/明天/本周日程”“飞书日程”“飞书日历”时，必须调用 `calendar(action="list", source="feishu")`，不要凭记忆或历史上下文猜测结果。
- 日程查询结果必须格式化展示，突出 `🕒 时间`、`📍 地点`、`⭐ 主体事件` 和 `💡 建议`。
- 用户询问“检查日历认证状态”时，必须调用 `calendar(action="status")`，不要自行判断 App ID、App Secret 或 token 是否存在。
- 当前日历主线是飞书私人日历 OAuth；钉钉仅作为可选消息通道，不作为日历查询来源。
- 用户明确要求手动创建或修改日程时，使用 `calendar` 草案和确认流程。

## 生活事件

- 邮件、QQ/飞书/钉钉消息中出现面试、会议、体检、聚餐、航班、酒店等高置信日程事件时，生活事件管家会先结构化格式化，再自动写入飞书日历。
- 写入飞书日历前必须保证标题、时间、地点、联系人、来源和原始摘要被整理清楚；不要把混乱原文直接作为日程标题。
- 日程标题和描述可以使用轻量表情符号突出重点，例如 `📌【会议】项目同步会`，描述中保留 `⭐重点`、`🕒时间`、`📍地点`、`💡建议`。
- 缺少开始时间时不要写入日历，应通过当前聊天渠道询问缺失时间；后台巡检才使用默认通知渠道。
- 写入或修改飞书日历成功后，必须通过当前聊天渠道通知用户；后台巡检才使用默认通知渠道。
- 查看处理记录使用 `life_event(action="list")`，重新巡检邮件使用 `life_event(action="reprocess_email")`。

## cron

- 定时提醒必须使用 `cron` 工具创建、查看或删除任务。
- 不要只把提醒写入 `MEMORY.md`，那不会触发实际通知。
- 周期性任务应写入 `HEARTBEAT.md`，并用文件工具维护。

## exec

- 命令默认有超时和输出截断。
- 文件操作优先限制在 workspace 内。
- 不要用 `exec` 绕过已有专用工具，例如日历、提醒、记忆和消息发送。

## 模型失败

- 首选大模型额度不足或 API 调用失败时，系统会自动切换到备用模型。
- 额度类错误当天会跳过首选模型，次日再重新尝试。
- 不要把供应商错误、模型名、quota、HTTP 细节或堆栈原样发给用户。
## 主动规划

- 用户要求“安排今天”“根据日程规划”“重新规划”“顺路处理待办”时，必须调用 `daily_plan`，不要只凭记忆编排。
- `daily_plan(action="plan_day")` 和 `daily_plan(action="reschedule")` 只生成建议，不会自动修改飞书日历。
- 如果用户明确要求把规划写入或改期到飞书日历，必须再调用真实 `calendar` 或 `life_event` 工具。
- 规划输出应突出时间、地点、主体事件、缓冲风险和个性化依据。

## 情境感知提醒

- 用户询问天气风险、交通风险、日程冲突、是否来得及、是否需要预警时，必须调用 `smart_reminder`，不要凭空判断天气或路线。
- `smart_reminder(action="check_risks")` 用于检查未来天气、交通、账单截止和日程风险。
- `smart_reminder(action="route_risk")` 用于基于高德地图评估两个地点之间的通勤耗时。
- 智能提醒默认只给预警和建议，不会自动修改飞书日历；用户明确要求改期或写入时，再调用真实日历工具。

## 出行旅行规划

- 用户提出周末出游、去某地旅行、前往商场、临时外出、路线加行程、预算加行程时，必须调用 `outing_plan`。
- `outing_plan` 会结合 RAG、飞书日历、高德路线/天气和 Web 搜索生成建议；不要凭空编造攻略、营业时间、路线或天气。
- `outing_plan` 默认只生成规划建议，不会自动写入飞书日历；用户确认后再调用 `calendar` 或 `life_event`。

## Web 搜索后端

- `web_search` 支持 Tavily 和 Brave 两种后端。
- `tools.web.search.provider="tavily"` 或 `apiKey` 以 `tvly-` 开头时使用 Tavily Search。
- 出行、旅行、购物和攻略类请求需要真实调用 `web_search`；不要凭空编造当前攻略、营业时间、价格或避坑信息。

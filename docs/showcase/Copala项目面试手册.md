## 1. 项目简历内容拆解

### 1.1 一句话定位

Copala 不是从零开发的通用 Agent 框架，也不是拥有通用 Planner、任务 DAG 和断点恢复能力的长任务 Runtime。更准确的定位是：

> 在 nanobot 轻量 Agent Runtime 之上，引入确定性领域控制面、结构化长期记忆和主动副作用编排，构建面向个人事务的领域自主 Agent。

“领域自主”仅指日历、出行、提醒、日内规划和 LifeEvent 等已经显式建模的场景，不能外推为通用复杂任务自主规划。

### 1.2 能力归属

| 能力 | nanobot 原生已有 | Copala 的真实增量 |
| --- | --- | --- |
| Agent 执行 | Agent Loop、LLM Tool Calling、最大迭代限制 | Tool Loop 前的确定性领域快路径与 LifeEvent 条件处理 |
| Tool / MCP | ToolRegistry、Schema 校验、MCP 动态注册 | 新增领域工具与领域服务；没有重写统一工具市场 |
| Memory | Session JSONL、`MEMORY.md`、`HISTORY.md`、摘要归档 | SQLite 结构化记忆、FTS5/BM25、signed-hash Dense、RRF |
| Provider / 模型 | Provider 抽象、模型适配及相关路由能力 | 不是当前简历三条的核心原创增量 |
| Sub-Agent | SpawnTool、后台子任务、结果回传 | 未新增多 Agent 分工协议、共享状态或任务图 |
| Automation | Cron、Heartbeat | LifeEvent 识别、执行门控、领域状态与提醒/日历/记忆联动 |
| Skills | Skills 发现和渐进加载 | LearnSkillTool 增加本地技能制品；Skills 本身不是原创 |
| 规划 | LLM 可通过工具逐轮执行 | 固定领域编排与贪心日程算法；不是通用 Planner-Executor |

### 1.3 三条简历描述的真实技术含义

#### 混合决策控制面

- 技术问题：所有请求进入 LLM 会造成意图冲突、工具选择波动、无谓 Provider 调用和副作用不可控。
- 核心机制：`DIRECT_ROUTES` 依次尝试 Calendar、Outing、SmartReminder、DailyPlanning；处理器返回文本即终止，返回 `None` 才继续 LifeEvent 和 LLM Tool Loop。
- 能力提升：确定性个人事务可绕过模型，开放请求仍保留 LLM 长尾推理。
- 真实边界：它是规则谓词加固定优先级，不是学习式路由器或动态 Planner。

#### 主动事件执行链

- 技术问题：Cron/Heartbeat 能定时触发，但不能判断普通消息中哪些信息应转化为日程、TODO 或提醒。
- 核心机制：确定性关键词、正则和否定规则抽取事件，再按类型、置信度和时间完整性编排 SQLite、飞书日历、Cron、Memory 与通知。
- 能力提升：Agent 能从被动回答推进到有条件地产生领域副作用。
- 真实边界：LifeEvent 状态持久化不等于整个 Agent 任务具备 Checkpoint；当前跨飞书、SQLite、Cron 和 Memory 也没有分布式事务。

#### 记忆驱动韧性规划

- 技术问题：Markdown 摘要难以按当前问题召回，单个外部服务失败可能拖垮整条规划链。
- 核心机制：BM25 与本地 signed-hash 分别召回后用 RRF 合并；出行规划固定读取记忆、日历、高德路线/天气和 Web，并对单源异常局部降级。
- 能力提升：跨会话偏好可进入当前规划，部分依赖不可用时仍能返回结构完整的结果。
- 真实边界：步骤拓扑固定，日内安排使用贪心算法；没有执行期动态 Re-plan、Reflection、任务 DAG 或步骤恢复。

### 1.4 明确不存在的机制

- 通用 Planner-Executor、任务 DAG、通用任务状态机。
- Reflection、自我批判、基于 Tool 结果自动修改执行图。
- 步骤级 Checkpoint、崩溃后断点续跑、跨进程长任务恢复。
- Copala 新增的 Multi-Agent 协作协议；Sub-Agent 主要来自 nanobot。
- 基于成本、权限、健康度和时延的统一 Tool/MCP/Skill/模型调度器。
- Redis、MQ、MySQL、微服务、生产集群与完整可观测平台。

## 2. 3～5 分钟项目介绍示范

下面是一版可以直接练习、但必须补充个人信息的候选人口吻介绍：

> 我做的项目叫 Copala，是一个面向个人事务的主动式 Agent，目前定位为本地 Alpha 和作品展示，目标场景是用户通过聊天入口管理日程、出行、提醒和长期偏好。项目选择 nanobot 作为轻量运行时，是因为它已经提供了 Channel、Provider、LLM Tool Loop、MCP、Sub-Agent、Cron/Heartbeat 和 Skills 等通用能力，我可以把重点放在 Agent 如何决策、如何积累上下文以及如何安全地产生副作用上。
>
> 我分析原生链路后发现三个问题。第一，高频、规则明确的请求也进入 LLM，不仅有额外调用，还可能选错工具；混合意图和写日历等副作用也不够可控。第二，Cron 只能按既定时间触发，系统不能从普通消息中识别面试、航班、账单等值得主动处理的事件。第三，Markdown 摘要不适合根据当前任务做精确召回，出行规划中的日历、路线、天气或搜索任一失败也可能影响整条结果。
>
> 整体上项目是本地单进程、异步事件驱动的模块化单体。Channel 把 QQ、飞书或邮件消息统一成 `InboundMessage`，经进程内 `asyncio.Queue` 交给 `AgentLoop`。我在原 Tool Loop 前增加了确定性领域控制层，按 Calendar、Outing、SmartReminder、DailyPlanning 顺序判断。命中后直接调用领域服务并终止，不请求模型；未命中时先做 LifeEvent 条件处理，最后才进入原有 LLM+Tools 慢路径。慢路径仍由 ToolRegistry 向模型提供工具 Schema，工具结果逐轮回填，并用最大迭代次数限制循环。
>
> 第二条主链是 LifeEvent。它通过关键词、正则和否定过滤识别事件类型，抽取时间、地点、联系人和金额，再依据事件类型、置信度和时间完整性进行门控。会议、面试和航班等可写入飞书日历，账单、快递等沉淀为 TODO，并创建 Cron 提醒和长期记忆。事件状态存 SQLite，`source_ref` 参与去重，避免相同来源的顺序重放重复处理。这里我会明确说它是领域执行链，不是通用工作流引擎。
>
> 第三条是长期记忆和多源规划。项目把对话、邮件、日历和规划产物保存为结构化记录，使用 FTS5/BM25 与192维本地 signed-hash 特征向量分别召回，再用 RRF 合并，并限制注入模型的上下文长度。出行规划固定组合记忆、日历、高德路线、天气和 Web 信息，每个来源有独立错误边界；日内规划则根据固定日程、任务优先级、时长和空档做贪心排程。它的价值是确定性和可测试性，而不是通用 DAG 或动态 Re-plan。
>
> 离线评测方面，60条冻结留出路由指令上 Accuracy 和 Macro-F1 均为100%，40条快路径样本未触发 Provider；LifeEvent 在48条留出样本上检测 F1 为98.6%；200条记忆、30条留出查询上的 Recall@5 为90%；32个依赖失败场景都输出了满足固定章节契约的降级结果。这些数据来自固定 Commit 的离线集和故障注入，不代表生产准确率、真实 API 时延或 Token 节省。
>
> 项目共【待补充真实人数】人，我的角色是【待补充：独立开发者/核心开发/架构设计】。我独立完成【只填写真实模块】，与【待补充成员角色】共同完成【待补充协作内容】。nanobot 原生的 Channel、Provider、MCP、Sub-Agent 和 Cron/Heartbeat 不属于我的原创贡献，我的个人工作边界是【待补充并准备 Commit/PR 证据】。

## 4. 核心业务流程

### 4.1 分层路由与慢路径

1. Channel 将消息转换为 `InboundMessage`，放入 `MessageBus.inbound`。
2. `AgentLoop` 按 `channel:chat_id` 加载 JSONL Session。
3. `_dispatch_direct_route` 顺序调用 Calendar、Outing、SmartReminder、DailyPlanning 处理器。
4. 处理器返回文本则终止本轮并保存 Session；返回 `None` 才检查下一路由。
5. 快路径未命中后执行 LifeEvent 条件处理。
6. LifeEvent 未生成终止响应时，`ContextBuilder` 组合 System Prompt、Session、RAG 记忆和当前消息。
7. Provider 返回 Tool Call 后，`ToolRegistry` 逐个执行并回填结果，最多循环 `max_iterations` 次。
8. 最终响应经过后端错误净化与未验证日历写入声明校验，再保存 Session 和回合记忆。

Calendar 直接查询目前仅对 QQ 开启；Outing、SmartReminder 和 DailyPlanning 的直接路径仅对 QQ/飞书开启。不能概括为所有 Channel 行为完全一致。

### 4.2 LifeEvent 主动事件链

1. 过滤知识问答、否定表达和仅描述历史的文本。
2. 通过关键词确定会议、面试、体检、航班、酒店、账单等类型。
3. 通过正则提取时间、地点、联系人和金额。
4. 由 `source + source_ref + type + title + start` 生成去重键并查询 SQLite。
5. 日历型事件缺时间时保存 `missing_time`；置信度不足时保存 `low_confidence`。
6. 条件满足时检查冲突并调用飞书 Provider 创建或更新事件；TODO 类型保存本地状态。
7. 创建一次性 Cron 提醒，把事件沉淀到 Memory，并向当前或默认 Channel 返回通知。
8. 日历调用失败时保存 `calendar_failed`。

一致性边界：远端飞书写入、本地 SQLite、Cron 和 Memory 不是一个原子事务。当前 `lifeEvents.calendarWriteMode` 虽存在于 Schema 和文档，但生产路径没有读取它，LifeEvent 直接调用 Provider；这是高风险技术债，面试时必须主动承认。

### 4.3 记忆驱动的多源规划链

1. 路由识别出行意图并调用 `OutingPlanningService`。
2. 确定性提取目的地和日期窗口。
3. 查询相关 Memory，读取飞书日程、高德路线、高德天气和 Web 信息。
4. 每个来源独立捕获异常：记忆/日历失败返回空结果，路线/天气返回错误字段，Web 失败返回不可用说明。
5. 按固定章节渲染日程校验、路线天气、外部信息、预算和备用方案。
6. 将规划产物重新写入长期记忆。

“降级成功”表示仍生成满足结构契约的文本，不等于计划事实完全正确或业务最优。

## 5. 核心技术架构解析

### 5.1 架构形态

Copala 是本地单进程、异步事件驱动的模块化单体，不是微服务：

```text
QQ / 飞书 / 邮件 / CLI 等 Channel
                ↓
       ChannelManager / MessageBus
          asyncio.Queue（内存）
                ↓
             AgentLoop
    ┌───────────┼────────────┐
领域终止快路径  LifeEvent   LLM Tool Loop
    ↓              ↓             ↓
Calendar / Planning / Reminder / ToolRegistry / MCP
    └───────────┬────────────┘
                ↓
SQLite / JSONL / Markdown / Cron jobs
                ↓
飞书日历 / 高德 / Web Search / LLM Provider
```

### 5.2 分层职责

| 层级 | 核心模块 | 作用与边界 |
| --- | --- | --- |
| 接入层 | `channels/`、CLI | 多通道消息适配；大部分来自 nanobot |
| 传输层 | `MessageBus` | 两个进程内 `asyncio.Queue`；不是耐久 MQ |
| 控制层 | `routing.py`、`AgentLoop` | 固定优先级决定是否绕过 LLM |
| 事件层 | `LifeEventExtractor/Manager` | 抽取、门控、落库和副作用调用 |
| LLM 层 | Provider、ContextBuilder、ToolRegistry | 原生 Tool Loop 慢路径 |
| 领域层 | Daily/Outing/Reminder/Calendar | 确定性个人事务算法 |
| 记忆层 | MemoryRAGStore、SessionManager | SQLite、JSONL 与 Markdown 双层记忆 |
| 调度层 | Cron、Heartbeat | 上游调度基座，Copala 增加领域回调 |
| 外部层 | 飞书、高德、Web、MCP、LLM | 有局部异常处理，无统一熔断与切换 |
| 验证层 | evaluation、pytest、Ruff | 冻结集、故障注入与工程回归 |

### 5.3 记忆数据结构与复杂度

- `memory_items` 保存类型、文本、来源、置信度、优先级、过期时间和 metadata。
- `memory_fts` 是 FTS5 虚表；`memory_embeddings` 用 JSON 保存192维向量。
- RRF 先合并两路排名，再叠加 priority 和 confidence，最后过滤过期项。
- `ContextBuilder` 通过 Top-K 和 `max_context_chars` 控制注入长度。
- `_dense()` 当前读取所有未删除向量，在 Python 中反序列化并计算余弦，复杂度近似 `O(N×D)`。
- `upsert_many()` 逐条连接和提交，10,000条索引耗时85.50秒，仍有明显优化空间。

### 5.4 已有可靠性与缺口

已有：固定路由优先级、Tool Loop 最大迭代数、局部错误边界、LifeEvent 去重、Tool Result 截断、输出净化、Session/事件/记忆/Cron 本地持久化、离线故障注入。

缺少：Durable Task、步骤状态、Checkpoint、跨系统补偿、全 Turn Deadline、统一重试/熔断、完整 Trace、生产权限模型、多 Agent 共享状态。

## 8. 技术深挖题

### Q09【中级，★核心详解】路由优先级如何工作，混合意图会不会丢失？

**回答要点：** 顺序为 Calendar、Outing、SmartReminder、DailyPlanning；命中即终止。当前没有多意图拆解，“明天去杭州开会并查天气”可能被一个路由提前消费，需结构化意图集合和写操作确认来演进。

### Q10【高级，★核心详解】Tool、MCP 和领域服务到底由谁选择？失败会自动切换吗？

**回答要点：** 领域快路径由 Copala 控制面选择；慢路径 Tool/MCP 仍由 nanobot 原生 Tool Loop 和模型选择。仅领域服务显式实现了局部降级，不存在全局 Tool Fallback Engine。

### Q11【中级】LifeEvent 为什么不用 LLM 抽取？

**回答要点：** 规则方案离线、确定、低成本、可测试；缺点是语义覆盖有限。合理演进是规则高召回、轻量模型复核、高风险写操作确认，而不是直接让 LLM 写日历。

### Q12【高级，★核心详解】`source_ref` 去重能保证 Exactly Once 吗？

**回答要点：** 不能。当前只证明20组同源顺序重放被抑制；先查后写存在并发竞态，远端成功本地失败也会造成重复。需要原子 PENDING、幂等键、Outbox/对账和补偿。

### Q13【中级，★核心详解】Copala Memory 相比 nanobot Memory 增加了什么？

**回答要点：** nanobot 有 Session 与 Markdown 摘要；Copala 增加带来源、类型、置信度和 metadata 的 SQLite 记忆，以及按当前查询的混合召回。两层并存但存在双写一致性问题。

### Q14【中级】192维 signed-hash 是真正的 Embedding 吗？

**回答要点：** 不是神经 Embedding，是中文字符/bigram与英文 token 经 BLAKE2b 映射到192个带正负号的桶，再做余弦。优势是本地确定，缺点是碰撞和语义泛化弱。

### Q15【高级，★核心详解】RRF 如何融合，实际收益有多大？

**回答要点：** 两路排名按 `1/(rrf_k+rank)` 累加，再叠加 priority/confidence。留出集 Dense 与 RRF Recall@5 都是90%，RRF 仅把 MRR@5 从0.7028提高到0.7111，不能说显著提升召回。

### Q16【高级】SQLite 有哪些表，事务与并发边界是什么？

**回答要点：** Memory 有主表、FTS、向量和来源表；LifeEvent 有事件、提醒、通知去重表。单条 upsert 内部一致，批量逐条事务；无完善 WAL、busy timeout 和多实例治理，适合本地低并发。

### Q17【高级，★核心详解】“重新规划”是否属于动态 Re-plan？

**回答要点：** 不是。DailyPlanning 是重新运行同一贪心排程，OutingPlanning 是固定多源流水线；没有持久化任务图、已完成步骤状态或基于 Tool 结果重算未完成子图。

### Q18【专家】如何控制 Context、Token 和无限循环？

**回答要点：** Top-K、`max_context_chars`、Session `memory_window`、Tool Result 500字符截断、最大 Tool Loop 40轮。当前主要按字符和消息数控制，不是精确 tokenizer 预算，也未检测重复 Tool 调用模式。

## 9. 架构设计题

### Q19【高级，★核心详解】为什么是模块化单体？流量增长10倍哪里先出问题？

**回答要点：** 单用户本地 Agent 无需微服务；最先出现的是全局串行处理、外部调用累积、Dense 全表扫描和本地 SQLite/文件并发写，而不是服务发现问题。先按会话并行和持久层演进，不盲目拆服务。

### Q20【高级】为什么 MessageBus 不使用 Kafka 或 RabbitMQ？

**回答要点：** 当前是单进程本地场景，`asyncio.Queue` 简单且无运维成本。它不耐久、不跨进程；若需要多实例、峰值削峰和消费恢复，再引入耐久队列。

### Q21【高级】如果设计真正的 Planner-Executor，你会怎么做？

**回答要点：** 增加 `task_run/task_step/dependency`，受限 Schema 的 Planner，Executor 状态机，retry/fallback/skip/replan/manual 策略，幂等副作用和循环检测；现项目尚未实现。

### Q22【专家】如何设计长任务 Checkpoint 与恢复？

**回答要点：** Tool 前保存 PENDING 和输入哈希，Tool 后保存输出摘要、外部副作用 ID 与状态；重启扫描未完成步骤。只读可重放，写操作必须查询外部状态或依赖幂等键。

### Q23【高级】如何把单意图路由升级为多意图任务图？

**回答要点：** 先输出结构化意图集合，再标注依赖、读写属性和确认要求；确定性规则处理高置信意图，低置信回退 LLM；最终按依赖执行，而不是第一个命中即终止。

### Q24【高级】Sub-Agent 是否等同 Multi-Agent？

**回答要点：** 不等同。上游 Sub-Agent 是主 Agent 启动后台 Tool Loop 并收回结果，没有角色协商、共享黑板、任务 DAG、冲突处理或 Checkpoint。

### Q25【专家】怎样设计 Agent 可观测性？

**回答要点：** 为每轮生成 run_id/step_id，记录 route、模型、Tool、耗时、Token、状态、重试、错误分类和外部 correlation ID；敏感参数只保留脱敏摘要，使用结构化日志或 OpenTelemetry。

## 10. 性能优化题

### Q26【中级】性能数据是怎么测的？能推出 QPS 吗？

**回答要点：** Windows 11、Python3.13.14、20个查询、预热后3轮；报告P50/P95中位数和范围。它是单机离线查询延迟，没有并发压测、排队时间与资源指标，不能推出QPS。

### Q27【高级，★核心详解】为什么10,000条记忆 P95 接近0.69秒？

**回答要点：** `_dense()` 全量读取 JSON 向量、逐条反序列化、Python 余弦和全排序，近似 `O(N×D)`；1,000到10,000条延迟近似线性。

### Q28【高级】索引85.50秒如何优化？

**回答要点：** 当前 `upsert_many()` 逐条连接与事务。先复用连接、批量事务、`executemany`，再换紧凑向量存储；超过万级后评估 SQLite Vector、HNSW 或 FAISS。

### Q29【高级】多源规划为何没有并行请求？怎样安全并行？

**回答要点：** 当前顺序 `await` 简单但累积时延。目的地确定后，日历、天气、路线、Web和Memory中无依赖部分可 `gather(return_exceptions=True)`，同时设置总 Deadline、依赖 Semaphore 和单源超时。

### Q30【专家】如何设计可靠的性能对比实验？

**回答要点：** 固定数据和硬件，区分冷/热缓存；至少多轮并报告范围；记录CPU、内存、I/O、并发数和查询分桶；对优化前后做相同输入与统计显著性检验。

## 11. 线上故障排查题

> 项目当前没有生产事故。以下是“如果生产化”的排障题，回答时不能伪装成亲历事故。

### Q31【高级，★核心详解】高德、Web 或 Provider 变慢/失败，如何止损和定位？

**回答要点：** 查并发入口、长事务和连接释放；临时降并发并重试可重试写；随后批量缩短事务、配置 WAL/busy timeout、单写队列。多实例场景需迁移真正服务型数据库。

### Q33【专家】Tool执行三步后进程崩溃，如何恢复？

**回答要点：** 当前不能步骤恢复，本轮消息在结束后才整体保存，外部副作用可能已发生。止损是查询外部状态和人工对账；长期引入 Durable Run、幂等副作用和补偿。

### Q34【高级】用户发现重复日历事件，如何排查？

**回答要点：** 根据 `source_ref`、去重键、外部 event_id 和时间线判断并发、不同 message_id 或远端成功本地失败；临时关闭 LifeEvent direct 写入，清理重复并回补状态；修复为原子占位和对账。

### Q35【专家】模型突然大量超时，排障链路是什么？

**回答要点：** 现象→按 Provider/模型统计→看队列与全局锁→查网络/429/配额→切备用或降级→限制并发→复盘。不得声称现有 Fallback 覆盖所有异常路径。

## 13. 每类问题的详细参考回答（12道核心详解）

### 核心题1：Q01 nanobot 与 Copala 的能力边界

**面试官问题**

nanobot 原生已经有 Agent Loop、Memory、MCP、Sub-Agent 和 Automation，你这个项目真正新增了什么？

**面试官为什么问**

判断候选人是否真正读过上游源码，还是把 Fork 项目原有能力全部包装成个人成果。

**高质量参考回答**

我的结论是，Copala 没有重新发明通用 Agent Runtime。nanobot 原生负责多 Channel、Provider、ToolRegistry、LLM Tool Loop、MCP、Sub-Agent、Cron/Heartbeat、Skills、Session 和 Markdown Memory。Copala 的增量集中在三个方面：第一，在原 Tool Loop 前增加确定性领域控制面；第二，把普通消息转为有状态的 LifeEvent 副作用链；第三，把摘要记忆扩展为结构化混合检索，并将记忆、日历、路线、天气和 Web 固定编排为领域规划。

我不会把 MCP、Sub-Agent 或 Cron 写成原创，也不会说项目已有通用 Planner、DAG 和 Checkpoint。选择 nanobot 是因为它足够轻，可以直接修改主执行链；代价是长任务持久化和多 Agent 协作需要后续自己补齐。

**实现细节**

增量代码主要落在 `agent/routing.py`、`life_events/service.py`、`agent/memory_rag/`、`planning/`、`smart_reminders/` 和离线 `evaluation/`。个人实际负责哪些文件必须结合【真实 Commit/PR】回答。

**递进追问及回答**

1. **问：为什么不能通过 Git diff 直接证明全部增量？**
   答：仓库首个可见提交已经包含二次开发内容，缺少纯净上游快照的完整演进链；需要对照 nanobot `v0.1.4.post4` 做类级和机制级审计。
2. **问：如果去掉 Copala 增量还能运行吗？**
   答：原生对话和 Tool Loop 仍能工作，但会失去确定性快路径、结构化记忆和主动事件闭环。
3. **问：个人贡献怎么证明？**
   答：提供本人真实的 Commit、PR、设计记录、测试和缺陷闭环；不能用项目存在替代个人归属证据。

### 核心题2：Q03 为什么增加确定性控制面

**面试官问题**

为什么不让 LLM 统一选择工具，而要在前面加固定路由？

**面试官为什么问**

考察概率型推理与确定性控制的边界，以及候选人是否理解副作用风险。

**高质量参考回答**

我的结论是，高频、意图明确并带外部副作用的请求不应完全依赖模型自由选择。原生 Tool Loop 适合开放任务，但查询日历、检查风险或生成固定领域计划时，模型调用增加成本和波动，还可能出现工具误选或“没有真实写入却声称成功”。Copala 因此先用可测试的领域谓词和显式优先级处理确定性场景，未命中再进入 LLM。

这种设计把控制面和推理面解耦：控制面负责风险边界与已知流程，LLM 负责开放长尾。代价是规则泛化有限，混合意图可能被首个命中路由提前终止，所以我称它为混合 Agent 架构，而不是更智能的通用 Planner。

**实现细节**

`AgentLoop._process_message()` 先调用 `_dispatch_direct_route()`，依次执行 `DIRECT_ROUTES`。处理器返回文本即保存 Session 并返回；返回 `None` 才继续。之后执行 `_auto_process_life_events()`，最后构建上下文并运行 `_run_agent_loop()`。

**递进追问及回答**

1. **问：为什么优先级是 Calendar、Outing、Reminder、DailyPlanning？**
   答：先放只读且意图窄的日历查询，再放目标明确的出行和风险检查，最后放覆盖面更广的日内规划，以降低误拦截；该顺序应由冲突集持续验证。
2. **问：LLM 能否覆盖规则未识别表达？**
   答：可以，未命中时仍走慢路径；但慢路径不会自动拥有与快路径完全相同的确定性保证。
3. **问：何时应该删除快路径？**
   答：若真实盲测证明误拦截高于收益，或领域规则变化频繁难以维护，应改为高精度候选器或统一结构化意图层。

### 核心题3：Q05 如何解释离线评测指标

**面试官问题**

路由100%、LifeEvent F1 98.6%、规划降级100%，为什么这些数据可信？

**面试官为什么问**

检验候选人是否理解数据泄漏、统计口径和离线指标的外推边界。

**高质量参考回答**

这些数字只用于确定性回归，不代表生产泛化。路由数据共180条，开发集120、留出集60；快路径计数测试是40条。LifeEvent 共120条，留出48条，其中 TP=36、FP=1、FN=0、TN=11，因此 Precision约97.3%、Recall 100%、F1约98.6%。规划共40个场景，其中32个注入依赖失败，成功定义是函数不抛异常且包含必要章节。

数据集冻结并保存哈希能够证明结果可追溯，但不能消除模板同分布、样本较小和标注者偏差。简历必须带“离线留出集/故障注入”口径，不能写生产准确率，也不能由40次 Provider bypass 推算 Token 节省。

**实现细节**

评测基线 Commit 为 `f4ecb42`，数据集总哈希为 `c7bfab38d7d07c20d6537298e6da5e2dc2988eb5c9841a9e770a17e1fc672178`；路由决策哈希为 `c969f463da08d53162a3f6582dad1d346b9508947d91037e3e4edff0443167d3`。

**递进追问及回答**

1. **问：冻结留出集为什么仍可能泄漏？**
   答：生产规则和数据模板可能共享关键词空间，即使具体记录没参与调优，模板结构仍可能同源。
2. **问：下一版怎样更可信？**
   答：让非开发者基于真实脱敏表达独立编写，按模板族切分，加入否定、错别字、省略、多意图和 OOD，并报告置信区间。
3. **问：293项测试能证明业务质量吗？**
   答：不能。重构后293/293只证明回归测试通过；核心指标报告仍绑定282项测试时点，两个时点不能混写。

### 核心题4：Q09 路由冲突与多意图

**面试官问题**

用户说“明天去杭州开会，查天气并写入日历”，系统如何拆解？

**面试官为什么问**

判断“自主决策”是否真的包含任务拆解，以及顺序终止路由是否丢信息。

**高质量参考回答**

当前不会生成通用子任务图，而是按固定优先级尝试路由，某一快路径返回文本就结束本轮。因此复杂混合请求存在被一个意图提前消费的风险。我不会把当前实现描述为自主任务拆解，它解决的是单一高置信领域意图的确定性执行。

更合理的演进是先把请求解析为结构化意图集合，例如 `calendar_write`、`weather_check`、`outing_plan`，再标注依赖和副作用等级。只读步骤可自动执行，写日历必须二次确认；低置信意图回退 LLM。这样才能从优先级路由升级为受限任务图。

**实现细节**

当前谓词是显式字符串规则，Calendar 查询会排除写入、规划和风险词，Outing 也会排除“写入日历”等词，以减少冲突，但不能覆盖所有自然语言组合。

**递进追问及回答**

1. **问：为什么不让 LLM 一次输出多个意图？**
   答：可以用于低置信补充，但高风险写操作仍要经过确定性策略和确认，不能仅信模型分类。
2. **问：任务图如何避免循环？**
   答：限制最大节点和深度，验证 DAG，无依赖变化时禁止重复 Re-plan，并记录相同输入/工具调用指纹。
3. **问：是否必须引入 LangGraph？**
   答：不必须；若图短且固定，可先用数据类加状态机。需要持久化和复杂分支后再引入框架。

### 核心题5：Q10 Tool、MCP 与能力选择

**面试官问题**

Agent 如何决定调用什么 Tool 或 MCP？工具失败后怎么切换？

**面试官为什么问**

区分 Copala 的领域路由与 nanobot 原生 ToolRegistry/MCP，并检查是否夸大统一调度能力。

**高质量参考回答**

系统有两套选择机制。确定性领域服务由 Copala 控制面直接选择；长尾 Tool 与 MCP 仍由 nanobot 原生 Tool Loop 把 Schema 提供给模型，由模型决定名称和参数。Registry 负责注册、类型转换、Schema 校验和执行，错误结果回填模型，模型可能在下一轮改参数或换工具。

因此当前不存在基于成本、权限、延迟、健康度的统一 Capability Scheduler，也不保证失败后自动切换。只有出行等领域服务显式实现的来源级降级，或模型理解错误后主动换工具，才会发生替代路径。

**实现细节**

MCP 工具动态包装后注册进同一 ToolRegistry；Copala 没有重写 MCP 协议。多个 Tool Call 当前按顺序 `await`，没有依赖分析或并发调度。

**递进追问及回答**

1. **问：两个工具都能查天气如何选择？**
   答：当前慢路径主要靠模型；领域出行固定使用高德。升级后可用能力标签、权限、成本、P95、健康度和幂等属性筛选。
2. **问：参数错误如何修复？**
   答：Registry 校验失败后将错误回填，模型下一轮修正；当前没有独立参数修复器。
3. **问：Tool成功是否等于业务成功？**
   答：不等于。返回字符串可能是降级或部分成功，应使用结构化状态并做后置断言。

### 核心题6：Q12 LifeEvent 的幂等边界

**面试官问题**

20组重复输入都被抑制，两个进程同时处理同一条消息还能只写一次飞书吗？

**面试官为什么问**

考察候选人是否把顺序去重包装成 Exactly Once，以及是否理解跨系统竞态。

**高质量参考回答**

不能保证。当前准确表述是“20组同源顺序重放被抑制”。去重键包含 source、source_ref、事件类型、标题和开始时间，本地还有唯一约束；但执行顺序是先查重，再调用飞书，最后 upsert 本地状态。两个并发请求可能都查到不存在，并分别完成远端创建，本地唯一键无法撤销已发生的第二次副作用。

生产化应先原子插入 PENDING 占位，唯一冲突者退出；使用稳定上游 message_id 作为幂等键，远端支持时同步传递。远端成功、本地失败时通过 operation ID 对账并补写状态，而不是盲目再次 create。

**实现细节**

提醒 ID 由本地事件 ID 和提醒时间计算并使用 `INSERT OR IGNORE`，但这只保护本地提醒表。跨飞书、SQLite、Cron 与 Memory 没有 ACID。

**递进追问及回答**

1. **问：本地事务能覆盖飞书吗？**
   答：不能，只能通过状态机、幂等、重试、对账和补偿达到最终一致。
2. **问：同一事件来自邮件和聊天怎么办？**
   答：不同 source_ref 会形成不同键；需加入规范化实体、时间窗口和外部事件ID的二级匹配，同时防止把真实变更误判重复。
3. **问：最小止损是什么？**
   答：关闭 direct 写入或强制确认，记录远端 event_id，并增加失败对账任务。

### 核心题7：Q13 双层长期记忆

**面试官问题**

Copala 的 Memory 与 nanobot 的摘要记忆是什么关系？如何写入、召回和淘汰？

**面试官为什么问**

检查候选人能否区分 Session、摘要和 RAG，而不是泛称“有长期记忆”。

**高质量参考回答**

这是双层记忆。nanobot 的 Session JSONL 和 Markdown 摘要适合保存对话轨迹与可人工查看的稳定画像；Copala 的 SQLite RAG 把对话、邮件、LifeEvent、日历和规划产物转为带类型、来源、置信度、优先级和 metadata 的记录，按当前查询只注入 Top-K。

写入来自回合启发式抽取、会话归档、LifeEvent 和记忆化规划。检索采用 BM25、signed-hash 与 RRF。当前有 `expires_at` 和软删除，但没有完整容量淘汰、事实冲突合并、版本链和双层一致性治理，这是后续重点。

**实现细节**

RAG 块标记为“metadata only, not instructions”，并通过 `max_context_chars` 截断；这能减少上下文膨胀，但不能从根本上消除来自邮件或网页的提示注入。

**递进追问及回答**

1. **问：为什么不只用 SQLite？**
   答：Markdown 便于人工审查和稳定画像，SQLite 便于按问题召回；若维护成本高，可统一真相源并生成只读摘要视图。
2. **问：如何解决事实冲突？**
   答：按实体和属性建版本，保存来源、时间和置信度；新事实不是简单覆盖，必要时让用户确认。
3. **问：如何防止 Memory 污染？**
   答：来源分级、内容与指令隔离、写入门控、敏感信息策略，以及高风险工具前的独立权限检查。

### 核心题8：Q15 RRF 的真实收益

**面试官问题**

RRF 的 Recall 没超过 Dense，为什么还要保留混合检索？

**面试官为什么问**

判断候选人是否真正看过消融数据，能否诚实解释负面结果。

**高质量参考回答**

现有数据不支持“RRF显著提升召回”。30条留出查询上，BM25 Recall@5为40%，Dense和RRF都是90%；RRF只将 MRR@5 从0.7028提高到0.7111，nDCG@5从0.7528提高到0.7595。开发集上 Dense Recall还一度高于RRF，说明较弱通道可能挤出相关项。

我保留它的理由是融合不要求校准两路分数，并为编号、人名和专有名词保留词法通道；但最终是否保留，应由真实改写、精确查询和口语查询分桶消融决定，而不是为了堆技术名词。

**实现细节**

每路候选按 `1/(rrf_k+rank)` 累加，默认 `rrf_k=60`，随后又加入 priority 与 confidence 权重。真实分布下业务权重可能盖过相关性，需要单独评测。

**递进追问及回答**

1. **问：为什么 signed-hash 在集上表现高？**
   答：查询与记忆可能共享大量词项和模板标识，不等于具备真正语义泛化。
2. **问：如何优化融合？**
   答：按查询类型动态加权，替换真实 Embedding/ANN，并用标注集训练或验证重排器。
3. **问：何时直接删除 BM25？**
   答：只有真实精确查询也证明无收益；通常专有名词和编号仍适合词法通道。

### 核心题9：Q17 规划与 Re-plan 的边界

**面试官问题**

你的“重新规划”是否包含 Planner-Executor、DAG 和动态 Re-plan？

**面试官为什么问**

防止候选人用 Agent 热词扩张固定算法的真实范围。

**高质量参考回答**

不包含。DailyPlanning 把飞书日程视为固定事件，从请求和 LifeEvent 收集可移动任务，按优先级、时长和标题排序，再贪心放入工作时段空档。“重新安排”只是重新运行同一算法并改变输出模式。OutingPlanning 也是依次取 Memory、Calendar、路线、天气和 Web 后渲染固定章节。

当前优势是确定、可解释、故障边界清晰；局限是不会生成未知步骤，不保存已完成子任务状态，也不会因为某个 Tool 返回结果而修改后续任务图。真正 Re-plan 需要持久化 run/step、依赖边和触发条件。

**实现细节**

规划评测40个场景只验证不抛异常和必要章节存在，其中32个依赖失败场景全部满足契约；这不代表路线、预算或行程最优。

**递进追问及回答**

1. **问：贪心算法可能失败在哪？**
   答：高优先级长任务可能挤掉多个短任务，也没有地点路线、截止时间和全局最优约束。
2. **问：为什么先用贪心？**
   答：单用户日程规模小，解释性和稳定性优先；约束复杂后可用 CP-SAT。
3. **问：什么条件触发真正 Re-plan？**
   答：前置步骤失败、外部状态变化、预算超限或用户约束改变，并且影响未完成依赖子图时触发。

### 核心题10：Q19 架构与扩展性

**面试官问题**

为什么做成单进程模块化单体？如果请求增加10倍哪里先出问题？

**面试官为什么问**

考察候选人能否基于实际规模选架构，而不是机械套用微服务。

**高质量参考回答**

当前是单用户本地 Alpha，单体能减少部署、网络和一致性复杂度，模块边界已通过 Channel、Bus、Agent、领域服务和持久层分开。10倍流量下首先遇到的不是服务发现，而是主处理串行等待、外部 API 时延累积、Dense 全表扫描和 SQLite/JSONL 并发写。

演进顺序应是先做观测和会话级并发，把可变 Tool Context 改为显式 TurnContext；为 Provider、MCP 和外部 API 加 Semaphore 与背压；再替换检索索引和持久层。只有团队、部署和伸缩边界真正独立后才拆服务。

**实现细节**

MessageBus 是进程内 `asyncio.Queue`，不耐久也不跨实例。Session 是 JSONL，Memory/LifeEvent 是 SQLite；直接横向扩容会面对重复调度、共享状态和文件一致性问题。

**递进追问及回答**

1. **问：为什么不用 Kafka？**
   答：当前单进程无需支付运维成本；需要跨进程耐久消费、削峰和重放时再引入。
2. **问：可以直接多进程启动吗？**
   答：不可以安全地直接扩；Cron可能重复执行，本地锁无效，SQLite和文件共享需要治理。
3. **问：第一项监控是什么？**
   答：分段耗时：队列等待、路由、Memory、Provider、Tool、外部API和持久化，并按 route/provider/tool 标签聚合。

### 核心题11：Q27 Memory 性能瓶颈

**面试官问题**

10,000条记忆检索 P95 为691.75ms，瓶颈在哪里，如何优化？

**面试官为什么问**

检查候选人是否读过实现、理解复杂度，并能解释测试而非只背数字。

**高质量参考回答**

瓶颈主要在 `_dense()`：每次查询从 SQLite 读取全部未删除向量，JSON反序列化后在Python逐条计算192维余弦并全量排序，复杂度近似 `O(N×D)`。因此1,000条 P95约68.92ms，10,000条约691.75ms，接近线性。索引也因 `upsert_many()` 逐条事务，10,000条耗时85.50秒。

优化顺序是先分段计时确认瓶颈，然后批量事务、连接复用和紧凑二进制向量；检索先按类型、时间或词法候选预筛；规模继续增大再使用 SQLite Vector/HNSW 或 FAISS。单用户万级前不一定需要独立向量数据库。

**实现细节**

数据来自本地 Windows 11、Python3.13.14，20条查询、预热后3轮，报告三轮中位数和范围。它不是线上RT，也没有并发压测，因此不能计算QPS。

**递进追问及回答**

1. **问：先换向量数据库还是先批量事务？**
   答：索引先做批量事务；查询先做候选预筛和剖析。确定规模边界后再换索引，避免过度架构。
2. **问：100,000条会是多少？**
   答：不能直接承诺；当前线性趋势说明会明显恶化，但需实测且可能受I/O和缓存影响。
3. **问：优化有效如何证明？**
   答：同数据、同硬件、同查询，报告冷/热、P50/P95/P99、CPU/内存与多轮范围。

### 核心题12：Q31 外部依赖故障治理

**面试官问题**

高德卡住30秒、Web限流、Provider抛异常时，系统如何降级？

**面试官为什么问**

区分立即抛错的Stub测试与真实超时、雪崩和资源耗尽治理。

**高质量参考回答**

当前领域规划对单源异常做了局部捕获，路线和天气返回错误字段，Web返回不可用说明，记忆和日历可以退为空结果。但故障注入主要模拟立即异常或错误字符串，没有覆盖慢响应、429风暴、连接池耗尽和级联超时；多源调用还是顺序执行，没有全Turn Deadline。

排障时我会先按阶段记录队列等待、路由、Memory、外部API和Provider耗时，临时关闭高延迟来源或切换为明确降级，避免错误确定性结论。长期为整轮设置Deadline，按依赖分配预算；只读且独立的来源并行；对5xx/超时做有限抖动重试，对认证和参数错误快速失败，写操作禁止盲目重试。

**实现细节**

现有成功标准是40/40产生结构结果，其中32个为失败场景；它没有测真实飞书、高德和Web网络时延。Provider Fallback也不能未经代码与测试证明就宣称覆盖所有异常。

**递进追问及回答**

1. **问：哪些来源可以并行？**
   答：目的地和时间窗口确定后，日历、Memory、天气和Web多数可并行；路线可能依赖地理编码，但可共享总Deadline。
2. **问：所有超时都重试吗？**
   答：不是。只读偶发超时可有限重试；写操作、认证错误和配额错误应快速失败或人工处理。
3. **问：怎样验证降级质量？**
   答：除章节存在外，检查来源标记、不可用项是否明确、是否虚构实时事实，并注入慢响应与畸形数据。

## 14. 递进式追问及回答

这一章用于训练“一个回答被连续向下追问”的稳定口径。每条链都应先回答事实，再讲权衡，最后说明当前缺口，不能为了显得高级而补造不存在的实现。

### 路由追问链

`为什么快路径` → `混合意图怎么办` → `误拦截如何发现` → `规则如何治理` → `什么时候引入任务图`

- 第一层：高确定性和高副作用任务需要可测试的控制边界。
- 第二层：当前没有通用多意图拆解，首个命中可能提前终止。
- 第三层：用通用请求误拦截率、冲突集和线上人工反馈发现问题；目前只有60条模板留出集。
- 第四层：规则集中声明、版本化、每次修改跑决策哈希，并为低置信请求回退 LLM。
- 第五层：出现动态依赖、长时间执行、部分完成和恢复需求后，再引入持久化任务图。

### 一致性追问链

`如何去重` → `并发怎么办` → `远端成功本地失败怎么办` → `进程崩溃怎么办` → `多实例如何恢复`

- 第一层：`source_ref` 与事件字段构造本地唯一键。
- 第二层：当前先查后写有竞态，唯一键不能撤销远端重复事件。
- 第三层：以 operation ID 查询飞书并补写本地状态，禁止盲目重试 create。
- 第四层：需要 PENDING 状态、持久化步骤和副作用 ID。
- 第五层：使用共享数据库原子抢占、Outbox、租约、对账和补偿；当前尚未实现。

### 记忆追问链

`为什么混合检索` → `RRF收益多大` → `为什么不用神经Embedding` → `规模扩大怎么办` → `记忆冲突和淘汰怎么办`

- 第一层：词法检索适合编号和专名，本地向量提供另一种相似性信号。
- 第二层：Recall没有提升，MRR绝对提升约0.0083，只能说轻微排序改善。
- 第三层：signed-hash零服务依赖且确定，但语义能力有限；不是神经Embedding。
- 第四层：先批量事务和候选预筛，超过规模边界再上ANN。
- 第五层：当前只有过期字段和软删除，缺少事实版本、冲突合并和容量淘汰。

### 规划追问链

`是不是Planner` → `是否动态Re-plan` → `故障为何还能输出` → `输出正确吗` → `何时升级DAG`

- 第一层：当前是固定领域编排，不是通用Planner。
- 第二层：重新规划是重跑算法，不保存执行中的已完成步骤。
- 第三层：每个来源局部捕获异常并保留明确不可用说明。
- 第四层：40/40只验证结构契约，尚缺事实一致性和人工质量评分。
- 第五层：任务需要未知步骤、依赖变化、部分恢复时引入DAG与Checkpoint。

### 性能追问链

`P95从哪来` → `机器和轮次` → `瓶颈证据` → `并发结果` → `10万条怎样`

- 第一层：本地Windows、Python3.13.14、预热后三轮，报告中位数和范围。
- 第二层：10,000条P95为691.75ms，索引85.50秒。
- 第三层：代码显示Dense全表JSON反序列化和Python余弦，1k到10k近似线性。
- 第四层：没有并发压测，不能推出QPS。
- 第五层：没有100k实测就不能外推，只能说明当前复杂度趋势不适合继续线性增长。

### 故障与安全追问链

`异常如何降级` → `超时如何处理` → `重试是否安全` → `如何熔断隔离` → `如何审计副作用`

- 第一层：现有领域服务把单源错误转为局部缺失或错误字段。
- 第二层：当前缺少整轮Deadline，慢调用覆盖不足。
- 第三层：只读偶发失败可有限重试，写操作必须幂等或确认。
- 第四层：未来按Provider/MCP/外部API设置Semaphore、Circuit Breaker和Bulkhead。
- 第五层：记录run/step ID、外部event ID、授权人、输入摘要和状态迁移；当前没有完整Trace。

### 压力问题的回答模板

当面试官说“这只是if-else”“指标是刷出来的”“不像你做的”时，按以下顺序回答：

1. 先承认合理质疑，不与错误前提争辩。
2. 收缩到真实能力边界，例如“领域控制面，不是通用Planner”。
3. 给一个可核验实现点和一个原始数据口径。

## 15. 项目可以进一步优化的地方

### P0：先解决可信度、正确性和安全

1. **重建独立评测集**：使用真实脱敏表达或由非开发者编写，按模板族和来源切分，增加多意图、否定、错别字、省略与 OOD。
2. **修复 LifeEvent 写入策略**：让 `lifeEvents.calendarWriteMode` 真正生效，默认 draft/confirm；禁止普通消息在未授权情况下直写真实日历。
3. **改造副作用状态机**：采用 `PENDING → REMOTE_CREATED → LOCAL_COMMITTED → NOTIFIED`，配合稳定幂等键、Outbox、重试和对账。
4. **增加 Durable Run 与 Trace**：建立 `task_runs/task_steps`，记录Step状态、外部关联ID、错误分类、Token和耗时。
5. **收紧安全默认值**：工作区限制默认开启，Shell运行在低权限沙箱，环境变量白名单，危险Tool审批，MCP/Skill信任清单。

### P1：性能与稳定性

6. **替换 Dense 全表扫描**：批量事务、紧凑向量、元数据预过滤；规模越界后使用SQLite Vector、HNSW或FAISS。
7. **建立端到端时间预算**：整轮Deadline、无依赖读取并行、有限重试、熔断、隔离舱和降级缓存。
8. **拆除全局串行瓶颈**：会话级锁、显式TurnContext、Provider/MCP Semaphore、有界队列与背压。
9. **结构化多意图路由**：保留高精度规则，增加置信度、多意图拆解、低置信回退和高风险确认。
10. **加强输出正确性验证**：把Tool结果改为结构化状态，校验真实副作用是否成功，而不只检查Tool名称或输出章节。

### P2：明确出现长任务需求后再做

11. **受限 Planner-Executor**：引入任务图、依赖、Checkpoint、Re-plan触发器、最大深度和循环检测。
12. **Capability Registry**：统一记录Tool/MCP/Skill的能力、权限、成本、时延、健康度和幂等属性。
13. **多 Agent 协作层**：只有确实需要角色分工和并行研究时，才增加上下文隔离、共享状态、仲裁和取消协议。

### 优化验收指标

- 路由：真实盲测集上的Macro-F1、误拦截率、多意图完成率。
- 一致性：并发重复副作用率、崩溃点恢复率、对账成功率。
- 性能：端到端P50/P95/P99、队列等待、Tool耗时、CPU和内存。
- 安全：未授权写操作拦截率、路径逃逸和Prompt Injection对抗结果。
- 规划：事实正确率、约束满足率、人工可执行性评分，而非只看章节存在。

| 维度 | 分值 | 评分标准 |

| 真实性与归属 | 25 | 能准确区分上游、项目增量和个人贡献，有证据，不编造 |
